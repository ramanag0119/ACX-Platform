# HMS Complete Data-Flow Audit

**Audit date:** 2026-10-16  
**Scope:** Current workspace source, registered FastAPI application, frontend route tree, and the configured PostgreSQL database.  
**Change policy:** Analysis only. No application source, schema, records, or migrations were modified. The two requested audit documents are the only intended project outputs.

## 1. Executive Summary

The project is a React/TypeScript frontend backed by a FastAPI/Python API and PostgreSQL via SQLAlchemy. The frontend has active API integration across the main dashboard and operational/configuration modules; this is not a static-only or frontend-only application.

Verified on this machine:

- 134 frontend `src` files, including 53 feature-module files and shared components/core/API files.
- 11 feature areas: `auth`, `bookings`, `common`, `config`, `dashboard`, `devices`, `marketing`, `occupancy`, `reports`, `services`, and `tickets`.
- 144 backend Python source/test files were discoverable in the backend tree; 19 `test_*.py` modules are present.
- FastAPI registers **161 HTTP operations** (including the root health operation). The source routers are assembled in `backend/app/api/v1/router.py` and mounted in `backend/app/main.py`.
- Read-only connection succeeded to PostgreSQL database `hms_db`, schema `public`. The connected schema has **93 tables** (92 application tables plus `alembic_version`) and **1,978 rows in total** at audit time.
- 92 ORM-mapped tables and all their column-name sets match the connected schema. The database has no extra business table; `alembic_version` is the expected migration metadata exception.
- Database revision is `0e2687233b59`; source contains child migration `7c4e2b9a1d53`, so that migration is pending in the connected database. It changes `service_status.name` id 3 from “Partially completed” to “In Progress”. No migration was run.
- Four in-process HTTP GET checks were made: `/health` **200**, `/api/v1/health/version` **200**, `/api/v1/health/db` **200**, and unauthenticated `/api/v1/facilities` **401**. No authenticated business response or mutation was tested.

**Grouped frontend findings:** 15, by primary category and not by every repeated literal: 1 static UI text group, 0 confirmed static operational records outside the mock/placeholder group, 2 hardcoded business-logic/calculation findings, 2 mock/placeholder groups, and 10 configuration groups. One separate migration-drift finding is included in the backend/data-integrity section. These counts are not a count of every label, color, page-size option, or repeated occurrence.

Highest-impact findings are the Facility Management editor's fixed demo content and non-persisting submit actions; a room-count calculation that uses at most one 100-row occupancy page; nationality form values not being saved and not matching the backend integer field; and the unapplied service-status migration. Some backend infrastructure metadata is available through an unauthenticated DB-health endpoint. Details, evidence and acceptance criteria follow.

Live database row counts are environment-specific and do not establish whether the connected records are production, demo, or test data. No guest names, contacts, credentials, tokens, database URL, or row contents are included here.

### 6.1 Backend hardcoded values versus valid configuration

- Status enums and lookup vocabulary in Pydantic schemas/filters are validation contracts, not mock records.
- Occupancy rules in `backend/app/services/occupancy.py` derive Occupied/Allotted/Unavailable/Available from stays, allocations, amenity status, and active conditions. They are backend business logic; the UI has presentation constants too.
- Energy summary groups/sums/counts real `energy_stat` records; the active-energy unit is resolved from `device_param`, not hardcoded in the UI.
- Seed scripts and `backend/seeds/` contain reference and sample/test records for populating the database. They are not API fallback responses; the connected database’s rows may be seeded, but that provenance is not proved for each record.
- API base URL and the backend database URL are environment-configured with development defaults; no credential values are reproduced here.

## 11. Data Not Queried, Exposed, Fetched, or Displayed

These labels are intentionally distinct:

- **A. Database data not queried:** Not proven for all 92 tables by name search alone. Models and support tables exist; scheduler, MQTT, command, access-key, import, and token tables require tracing their background/integration consumers before being called unused.
- **B. Queried but not exposed:** A full column-by-column service-query-to-response audit of every report and serializer was not completed. Fields in relationships can be omitted by response schemas; see Appendix B schemas and feature-specific mappings before asserting unused.
- **C. Exposed but not fetched by a feature page:** Country records are a confirmed example: 239 DB rows, `Country` model and seed data exist, but no countries route or frontend endpoint wrapper was found. The frontend defines endpoint functions/hooks for `GET /api/v1/invoices`, `GET /api/v1/device-current-stats`, `GET /api/v1/other-device-readings`, and `GET /api/v1/daily-data-points`, but a source search found no feature-page callers for those list hooks. The dashboard does consume the separate `/api/v1/daily-data-points/summary` hook, so this finding applies to the list endpoint, not all daily-data-point use.
- **D. Fetched but not displayed:** Some response properties are mapped to placeholders such as `"-"` (e.g. image fields when no display integration exists); not every response field is necessarily rendered. Exact all-field dead-field analysis is not proven here.
- **E. Incorrectly displayed:** Facility dialogs show fixed details; room availability fallback can hide missing status; nationality form does not save its selected value; status id 3 migration is pending; RoomView can undercount beyond one page.
